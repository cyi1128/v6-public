## 修复 1：扫描期间界面不全 —— 改为「写暂存表 + 扫完原子替换」

### 问题机制（改前）

`services/band_pattern_engine.py` 的 `scan_all()` 做的是：

```python
_con.execute('DELETE FROM pattern_record')   # ① 主表瞬间清空
...
_save_or_update(rec)                          # ② 每只股票逐条 INSERT 并 commit
```

全市场扫描要跑十几到二十几分钟，这期间：
- ① 执行后主表 0 条 → UI 刷新一次就是**空表**
- ② 期间主表条数从 0 慢慢涨到 361 → UI 刷新时看到的是**半截表**

日K建仓表每 5 分钟刷新一次，正好落在这段窗口里就会显示不全。

### 改法

| 改动点 | 内容 |
|---|---|
| 新增 `_STAGE_TABLE = 'pattern_record_new'` | 暂存表名 |
| 新增 `_WRITE_TABLE` | 当前写入目标表（扫描期指向暂存表） |
| `_init_db(table_name=None)` | 参数化，可建任意表名（含主键、字段补齐逻辑） |
| `_save_or_update(rec, table_name=None)` | 写入 `table_name or _WRITE_TABLE` |
| `scan_all()` 开头 | 建暂存表 → 清空暂存表 → `_WRITE_TABLE = _STAGE_TABLE` |
| `scan_all()` 结尾 | `_WRITE_TABLE = 'pattern_record'` → `_atomic_swap()` |
| 新增 `_atomic_swap()` | 一个事务内 `BEGIN IMMEDIATE` → `DROP TABLE pattern_record` → `ALTER TABLE pattern_record_new RENAME TO pattern_record` → `COMMIT`；失败则 ROLLBACK 并打印告警 |

关键点：**扫描全程主表 `pattern_record` 一动不动**，UI 读到的永远是上一次的完整结果；扫描结束时用一个毫秒级事务整体换上去。

## 修复 3：交易日历刷新

### 问题（改前）

`data/trade_calendar_cache.json` 只到 **2026-09-23**，导致：

- `get_latest_trading_date('2026-09-24 09:30')` 返回 **`2026-09-23`**
- 引擎 `_snapshot_trading_date()`（`services/intraday_opportunity_engine.py:158`）在 9:25 前把盘中状态写进**前一天**的 json（9/23 写进 9/22、9/24 写进 9/23，可复现）

而原有的 `refresh_from_market()` 刷不进去，实测两个原因：

1. **它调的源拿不到当天**：`get_kline_http('sh000001', 320, 'day')` 走新浪源，最后一根是 `2026-09-23`，**不含当天**
2. **更糟——它拿到的根本不是指数数据**：实测返回的最后一根是 `{'date': '2026-09-23', 'close': 11.6, ...}`，**上证指数当时在 3900 点附近**，11.6 明显是个股数据。等于原函数在往日历里灌错误日期

### 改法

`utils/trade_calendar.py`：

- 新增 `_fetch_index_dates_tencent(count=320)`：直连腾讯指数日K
  `https://web.ifzq.gtimg.cn/appstock/app/fqkline/get?param=sh000001,day,,,320,qfq`
  实测 **321 根、最后一根就是当天**（`['2026-09-24', '3925.32', '3900.00', '3930.50', '3895.22', ...]`）
- `refresh_from_market()` 改为：**腾讯指数源为主**，失败才回退 `get_kline_http`，且回退时加**「像不像指数」校验**（最高收盘价必须在 300~10000 点之间），否则丢弃并告警——避免个股数据污染日历
- 全部失败时保留本地缓存，绝不回退/清空

bat 里新增一步（放在交易日判断之后、扫描之前）：

```bat
echo [%date% %time%] [1/3] 刷新交易日历（腾讯指数日K） >> "%LOG%"
"%PYTHON_CMD%" -c "from utils.trade_calendar import refresh_from_market as _r; print('交易日历刷新：新增', _r(), '个交易日')" >> "%LOG%" 2>&1
```

### 验证

  [log] INFO 交易日历刷新成功：新增 1 个交易日，最新交易日=2026-09-24

## 修复 5（追加）：把「只主板 + 6 元以下剔除」加到 盘中机会 / 金铲子 / 联动

> 修复 4 只覆盖了**日K建仓模块**。你随后要求「加到盘中机会 金铲子联动模块」，本章记录这一轮的改动与验证。

### 5.1 先说架构，为什么不是「加一行过滤」那么简单

`services/intraday_opportunity_engine.py` 里，三个界面**共用一份内存数据**，但输出路径不同：

```
_fetch_quotes()        拉全市场行情 → self._quotes
      ↓
_detect_events()       涨幅/量比/量能异动 → self._events
      ↓
_build_clusters()      5 分钟窗口聚类 → self._clusters（含 path_codes / first_code）
      ↓
_update_opportunities() 集群内未启动的候选股 → self._opportunities
      ↓
   ┌──────────────┬──────────────────────┬───────────────────────┐
   ↓              ↓                      ↓
get_clusters()  get_opportunities()   get_gold_shovel_candidates()
  （联动表）       （盘中机会）            （金铲子）
                                              ↓
                                    再合并两路外部信号：
                                    ├ band_pattern_engine（波段四模式）
                                    └ anchor_tracker（基准阳跨日跟踪）
```

关键点：**联动表里的股票不存价格**，只有 `path_codes` / `first_code`（代码和名字）。
所以「6 元以下剔除」在联动表这一层，必须靠**外部价格**判断，不能像日K建仓那样读 `push_price` 字段。

### 5.2 改动清单（共 14 处）

| # | 位置 | 作用 |
|---|---|---|

### 5.3 验证过程中踩到的 4 个真实坑

**坑 1：金铲子的合并段绕过了过滤。**

**坑 4：行情完全拉不到时，联动表无法判断价格。**

### 6.3 换源带来的两个连锁问题，都补掉了

**问题 1：腾讯源没有量比字段。**

引擎的异动检测有三个触发条件，其中两个依赖量比：

```python
ANOMALY_VOL_RATIO = 2.0       # 量比 >= 2
ANOMALY_FIRSTSCAN_VR = 1.5    # 首扫量比 >= 1.5
```

而 `_parse_qq_quote()` 原本没解析量比 → 换源后异动检测会**整体失效**。

实测确认腾讯第 49 个字段就是量比（平安银行 2026-09-24 13:50）：

```
腾讯字段[49]           = 1.42
当日累计成交量         = 813624 手
最近5个完整交易日均量  = 814320 手   (日K volume 81432042 股 / 100)
已交易 170 分钟 / 240  = 0.708
推算量比 = 813624 / (814320 x 0.708) = 1.41   -> 与 1.42 吻合
```

→ 给 `_parse_qq_quote()` 补 `'vol_ratio': _f(49)`。

**问题 2：腾讯源没有行业字段（东财 f100）。**

`industry` 在引擎里用得很广：关系判定（`INDUSTRY_RELATED`）、板块涨幅（`_get_sector_pct`）、界面展示。
换源后这个字段会全空。

→ 新增 `_load_code_industry()`，从本地 `data/limit_up_reason.db` 的 `limit_up_reasons` 表建
「股票代码 → 行业」映射（**零网络**）。实测该表有 **3473 只**股票的行业，覆盖主板足够。
换源后行业填充率 **79.8%**。
