## 四、过程中抓出并修掉的 2 个致命 bug

这两个 bug 的共同后果都是**「脚本看起来正常，但扫描永远不会跑」**——正是最坑的情况。

### bug 1：`r'%~dp0'` 结尾反斜杠转义引号

- 写法：`sys.path.insert(0, r'%~dp0')`
- `%~dp0` 展开成 `D:\QuantMonitorV6\`（**结尾带反斜杠**）
- Python 里 `r'D:\QuantMonitorV6\'` 的结尾 `\'` **把收尾引号转义了** → `SyntaxError: unterminated string literal`
- Python 退出码非 0 → 被 `if errorlevel` 判成「非交易日」→ **每个交易日都跳过扫描**
- **修法**：删掉 `sys.path.insert`（`python -c` 默认已把当前目录加入 `sys.path`，且 bat 开头 `cd /d "%~dp0"` 已切到项目根），实测 `import` 正常。

### bug 2：`for /f` 嵌套双引号导致捕获失败

- 写法：`for /f ... in ('"%PYTHON_CMD%" -c "...print('YES' if ...)" 2^>nul')`
- 命令里同时有单引号和双引号，**`for /f` 解析失败** → 捕获不到输出 → `TRADING` 一直是默认值
- 后果：**交易日判断永远返回 YES**，周末节假日也会白跑一轮（13 分钟）
- **修法**：彻底放弃 `for /f`，改用 **`errorlevel` 精确匹配**：

```bat
set "IS_TRADE=1"
"%PYTHON_CMD%" -c "import sys;from utils.trade_calendar import is_trading_day;sys.exit(0 if is_trading_day() else 9)" >nul 2>&1
if errorlevel 9 if not errorlevel 10 set "IS_TRADE=0"
```

- 约定：非交易日返回退出码 **9**；`errorlevel 9 if not errorlevel 10` = **恰好等于 9**
- 判断代码报错返回 1、命令找不到返回 9009 → 都**不**满足「恰好 9」→ 保持 `IS_TRADE=1` → **fail-open**，照常扫描

### 附带修掉：日志乱码

- 现象：日志里 bat 的 `echo` 是 UTF-8（因为 `chcp 65001`），但 Python 子进程输出是 GBK → 同一文件混编码，中文全乱
- **修法**：bat 里注入 `set "PYTHONIOENCODING=utf-8"` + `set "PYTHONUTF8=1"`
- 小样本实测（bat echo + Python stdout + Python stderr 三种中文混写同一文件）：**能完整用 UTF-8 解码，替换字符数 0** ✅

## 五、怎么用

### 日常：什么都不用做
每个交易日 15:15 自动跑，日志写在 `D:\QuantMonitorV6\logs\auto_scan_YYYYMMDD.log`。

### 手动跑一次
- 图形界面：`Win+R` → `taskschd.msc` → 找到 `QuantMonitor_盘后扫描_四模式` → 右键「运行」
- 命令行：`schtasks /run /tn "QuantMonitor_盘后扫描_四模式"`

### 只验通路、不跑扫描（几秒出结果）
```cmd
cd /d D:\QuantMonitorV6
set SKIP_SCAN=1
盘后扫描_波段四模式_自动.bat
```
日志会出现 `SKIP_SCAN=1 自检模式：通路正常，跳过实际扫描`。

### 改触发时间
```cmd
schtasks /change /tn "QuantMonitor_盘后扫描_四模式" /st 15:30
```

### 停用 / 删除任务
```cmd
schtasks /change /tn "QuantMonitor_盘后扫描_四模式" /disable
schtasks /delete /tn "QuantMonitor_盘后扫描_四模式" /f
```

## 六、已知影响（务必知悉）

1. **扫描期间界面可能短暂不全（约 13 分钟）**
   `scan_all()` 是「先 `DELETE FROM pattern_record`，再逐条 INSERT」。15:15~15:28 之间如果日K建仓表正好刷新，会读到不完整数据。13 分钟后自动恢复完整。
   *可选优化*：改成「写临时表 + 原子替换」，需要动引擎，未做。

2. **主程序开着时扫描会慢，且日志被刷屏**
   主程序持有 `kline_cache.duckdb` 锁 → 扫描拿不到本地缓存 → 走在线源（pytdx/新浪/腾讯）→ 13 分钟。
   本次日志 356 KB，其中 `kline_cache 占用报错` 约 1000 行、`pytdx 降级报错` 约 2560 行。**有效信息在日志开头（链路）和结尾（结果）**。
   若想快：15:15 前关掉主程序，扫描能用本地缓存，会快很多。

3. **任务只在「用户已登录」时运行**
   这是 `/sc weekly` 的默认行为。如果 15:15 时没登录，当天不跑。

4. **本次验证把今天的日志清空了（我的操作失误）**
   转码脚本写文件时抛异常，但文件已被打开截断 → `logs\auto_scan_20260924.log` 变成 0 字节。
   验证证据（时间线、退出码、DB 写入时间）均已在前序输出中取得，未受影响；DB 未受影响。
   **今天 15:15 自动跑时会写入一份完整的、编码正确的日志。**

5. **`data\trade_calendar_cache.json` 仍只到 2026-09-23**（老问题，本次未动）
   `is_trading_day()` 靠「未来日期按工作日近似」兜底，所以判断结果正确；但引擎 `_snapshot_trading_date()` 在 9:25 前会把盘中状态归到「最近交易日」。是否修待你决定。
