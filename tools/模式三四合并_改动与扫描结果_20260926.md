## 五、关于「扫描卡死」的真实原因（重要）

你判断是「用了聚宽的数据」，实测**不是**。

**扫描取数链路**（`services\band_pattern_engine.py` L171\~185 `_load_bars`）：



```
def \_load\_bars(code):

&#x20;   try:

&#x20;       from services.kline\_cache\_service import get\_latest\_kline   # ① 本地 DuckDB 缓存

&#x20;       bars = get\_latest\_kline(code, count=120)

&#x20;       if bars and len(bars) >= 30:

&#x20;           return bars

&#x20;   except Exception:

&#x20;       pass

&#x20;   try:

&#x20;       from utils.kline\_fetcher import fetch\_kline                 # ② 腾讯在线兜底

&#x20;       bars = fetch\_kline(code, days=120)

&#x20;       return bars or \[]

&#x20;   except Exception:

&#x20;       return \[]
```

**全程零聚宽调用。** 聚宽回测文件本轮已移除。

**真实原因**：



1. **过滤顺序错了**——`scan_stock` 原本第 910 行先 `_load_bars(code)` 拉 K 线，到第 920 行才判断是不是主板。全市场 5221 只里 **2000+ 只是创业板 / 科创板 / 北交所**，每只都白跑一次在线取数（日志里 `[KLINE PYTDX] xxx 服务器180.153.18.170可连但无数据，快速降级HTTP源`，约 1.3 秒 / 只）。

2. **本地缓存只覆盖 3061 只**（`kline_cache.duckdb` 最新 2026-09-24），剩余股票必须走在线。

**已修**：过滤前置到取数之前。修复前后对比 ——



|        | 修复前     | 修复后               |
| ------ | ------- | ----------------- |
| 40 秒进度 | 约 400 只 | **1000 只**        |
| 降级噪音行数 | 大量      | **48 行**          |
| 全量结果   | 中断      | **5221 只跑完，异常 0** |
