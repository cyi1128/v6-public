## 三、第 2 层：异动检测（`_detect_events` L616）

**4 个触发条件，任一满足即记为一次异动**：

| # | 条件 | 阈值 | 事件类型 |
|---|---|---|---|
| 1 | 30 秒涨幅跳变 | ≥ **1.0%** 且 当前涨幅 > **0.5%** | `PRICE_ACCELERATION` |
| 2 | 量比 | ≥ **2.0** 且 当前涨幅 > **0.5%** | `PRICE_VOLUME` |
| 3 | 成交量跳变 | ≥ **2 倍** 且 当前涨幅 > **0.5%** | `VOLUME_EXPANSION` |
| 4 | 首扫（无基准） | 涨幅 ≥ **1.0%** 且 量比 ≥ **1.5** | `PRICE_VOLUME` |

对应常量：`ANOMALY_PCT_JUMP` / `ANOMALY_VOL_RATIO` / `ANOMALY_MIN_PCT` / `ANOMALY_FIRSTSCAN_PCT` / `ANOMALY_FIRSTSCAN_VR`（L52-56）。

**冷却机制**：

- 同一只股 **60 秒**内不重复报（`EVENT_COOLDOWN` L57）
- 冷却期内仍会刷新价格/涨幅/量比，且**涨幅 ≥5% 会把强度升为 `strong`**（L653-654）
- 30 分钟无更新的事件过期（`STALE_EVENT_SECONDS` L61）
- 强度判定：`涨幅跳变≥2.0 或 量比≥3.0` → `strong`（L690）

**首扫补时间**：程序刚启动时，用 `_backfill_anomaly_time`（L559）反查真实异动时间；查不到则标记 `历史异动时间未取得`。

**闭环动作**：每只异动股都调 `anchor_tracker.mark_anomaly()`（L697-703），把「今日异动股」告知基准阳跟踪器 → 盘后只跟踪这些股。

## 四、第 3 层：异动群聚类（`_build_clusters` L708）

**先清理**（L710-726）：

1. 剔除 6 元以下、ST 股的历史事件（同时清掉快照恢复带进来的）
2. 30 分钟无更新的事件 / 群，删除

**两轮聚合**：

| 轮次 | 关系类型 | 分组依据 | 最少股票数 |
|---|---|---|---|
| 1 | `DIRECT_CHAIN` 直接产业链（最高优先级） | `_stock_chains` 产业链映射 | ≥ **2** |
| 2 | `SAME_THEME` 同题材 | `_theme_map` 题材标签 | ≥ **2** |

常量 `CLUSTER_MIN = 2` L60、`CLUSTER_WINDOW = 300`（5 分钟）L59。

**扩散状态**（`_calc_diffusion` L810）：

| 状态 | 判定条件 |
|---|---|
| 扩散中 | 120 秒内 ≥ 2 只异动 |
| 扩散减弱 | 300 秒内 ≥ 2 只 且 最后异动距今 < 600 秒 |
| 扩散停止 | 最后异动距今 > 600 秒 |

**群内字段**（`_upsert_cluster` L761）：

| 字段 | 含义 |
|---|---|
| `first_stock` / `first_code` / `first_pct` | 首发异动股（按真实异动时间排序的第一只） |
| `first_event_time` | 首发真实异动时间（非发现时间） |
| `discovery_time` | 程序首次发现该群的时间（只在新建时固定） |
| `stock_count` / `active_count` | 群内已异动股票数 |
| `second_event_count` | 其中发生过二次异动的只数 |
| `cluster_total` | 该题材/产业链的**相关股票总数**（分母） |
| `event_density` | 联动密度 = 已动数 ÷ 相关总数 |
| `path_names` / `path_codes` / `path_times` | 实际轮动路径（按异动时间排序） |
| `actual_path` | 同上，带代码的 dict 列表 |

**关系判定四级**（`_relation_to_cluster` L830）：

```
DIRECT_CHAIN 直接产业链  >  CHAIN_MEMBER 链成员  >  INDUSTRY_RELATED 行业相关  >  SAME_THEME 同题材
```

中文映射 `REL_CN` L105：产业链 / 链成员 / 同题材 / 行业相关 / 未取得。

## 五、第 4 层：机会状态机（`_update_opportunities` L930）

### 5.1 候选池怎么来

```python
related = self._cluster_related(g)          # 该群全部相关股票
related.discard(g['first_code'])            # 只排除集群首发源
```

即：**群内除首发股之外的所有相关股票**，逐个过状态机。

### 5.2 两条产生路径

**路径 A —— 无自身事件 → 预备候选**（L956-1009）

| 门槛 | 条件 | 不满足时 |
|---|---|---|
| 集群扩散未停止 | `diffusion_state != 扩散停止` | 淘汰：`扩散停止` |
| 集群已形成 | `active_count >= 2` | 淘汰：`扩散未形成` |
| 自身未启动 | 涨幅 < 8% 且 涨幅 ≥ 0.3% | 淘汰：`已经启动或加速过快` |
| **现价 ≥ MA20** | `_tech_levels` 的 `ma20_above` | 淘汰：`跌破MA20` |
| 关系有效 | `rel_type != UNKNOWN` | 淘汰：`关系无效` |

全部通过 → 状态 **`预备`**，理由文案：`扩散中·{题材} 已动N只；自身待响应`

**路径 B —— 有自身事件**（L1011-1089）

先过 `_is_not_fully_started`（L896）：

```
涨幅 < 8.0%   且   涨幅 ≥ 0.3%   且   前一涨幅 < 5.0%
且不满足「涨幅≥6.0% 且 近期加速≥3.0」
```

| 情形 | 结果状态 |
|---|---|
| 首次事件（`event_count == 1`） | **`初步联动`** |
| 事件计数 ≥ 2 | **`二次异动`**；若扩散未停止 → 同轮升 **`联动确认`** |

### 5.3 状态迁移表（L1099-1160）

| 当前状态 | 触发条件 | 迁移到 |
|---|---|---|
| 预备 | `event_count ≥ 1` | 初步联动 |
| 初步联动 | `event_count ≥ 2` | 二次异动 →（扩散有效）联动确认 |
| 初步联动 | 距首次异动 ≥ **120 秒** 且无二次 | 冷却观察 |
| 冷却观察 | `event_count ≥ 2` | 二次异动 →（扩散有效）联动确认 |
| 二次异动 | 扩散未停止 | 联动确认 |
| 联动确认 | — | ATR跟踪（`_fill_atr` L1181） |
| ATR跟踪 | — | 持续刷新 ATR 参考（只读） |

**关键约束**：`processed` 集合保证**每只股每轮最多推进一次**（L933 / L1092-1095），防止一轮内连跳多级。

### 5.4 失效判断（L1162-1179）

| 条件 | 结果状态 | 理由 |
|---|---|---|
| 涨幅 ≥ **8.0%** | `已启动` | 已经启动（涨幅≥8%） |
| 集群扩散停止 | `失效` | 产业链扩散停止 |
| 近期加速 ≥ 3.0 且 涨幅 ≥ 6.0% | `失效` | 加速过快 |
| **15 分钟**无推进（`INVALID_TIMEOUT` L63） | `失效` | 长时间无推进 |

**注意**：失效判断在每次状态推进之后执行，**同一轮里新推进的状态也可能被立刻判失效**。

## 七、三个模块的关系（为什么容易看混）

```
_clusters（异动群，39 个）
   │
   ├─ get_clusters()  ──→  联动表   所有群，含首发/密度/轮动路径/扩散状态   20 群
   │
   └─ _cluster_related() → _update_opportunities() → _opportunities（候选，380）
                                                         │
                                                         ├─ get_opportunities() → 盘中机会  50 条
                                                         │
                                                         └─ get_gold_shovel_candidates() → 金铲子
                                                                                    + 基准阳跟踪
```

**同一个 `_opportunities` 字典，两个接口用不同条件取**：

- 盘中机会 = 排除失效/已启动 + 6元/ST 过滤 + 排序 + **截断 50 条**
- 金铲子 = 排除失效/已启动（同一条件）+ 6元/ST 过滤 + 排序 + **不截断** + 合并基准阳

所以正常情况下 **金铲子条数 ≥ 盘中机会条数**（实测 153 vs 50，差额主要来自基准阳合并段和 50 条截断）。

## 八、发现的问题（本次逐行核对抓出）

### 问题 1：MA20 缓存写入是死代码（真 BUG）

**位置**：`_tech_levels` L1512-1521

```python
            return {                        # ← L1512 这里已经 return 了
                'pressure': ..., 'ma20': round(ma20, 2),
                'ma20_above': (price is not None and price >= ma20),
            }
            self._ma20_cache[code] = (now_ts, result)   # ← L1520 永不执行
            return result                               # ← L1521 永不执行
```

`result` 这个变量**根本没定义过**（真跑会 NameError），但因为写在 `return` 之后，永远不会执行——所以**不报错，只是静默失效**。

**实测证据**：

```
_ma20_cache 初始: 0
首次 8 只耗时 0.23s (平均 28 ms/只)
调用后 _ma20_cache 条数: 0      ← 缓存没写进去
二次 8 只耗时 0.20s (平均 26 ms/只)   ← 没有变快，证明缓存从未命中
```

**来源**：**本来就有的**，不是我改出来的——7 个备份文件（包括改动之前最早的）全部包含这段死代码。

**实际影响**：

| 受影响的地方 | 后果 |
|---|---|
| `_prewarm_ma20_cache`（9:15-9:25 预热，L1839） | **完全白做**，缓存填不进去 |
| `_update_opportunities` L969（每个预备候选查一次） | 每轮重复查 K 线 |
| `get_clusters` L1684（每次 UI 刷新查一次首发股） | 每次刷新都查 |
| `_build_push_detail` L1330（推送时查一次） | 每次推送都查 |

按实测 26 ms/只 × 380 个候选 ≈ **每轮扫描多花约 10 秒**，而扫描间隔是 25 秒。
而且这段跑在后台线程，会持续占用资源——**这就是开盘时候选集中时界面发卡的主因之一**。

**修法**（一处改动）：把 L1512 的 `return {` 改成 `r = {`，然后在 L1519 的 `}` 之后接：

```python
            self._ma20_cache[code] = (now_ts, r)
            return r
```

**未修**，等你确认。

### 问题 2：`_maybe_push` 没有状态白名单（不是 BUG，说明一下）

`_maybe_push`（L1194）注释写着「预备/初步联动/冷却/ATR等待等中间状态只留在 UI，不再轰炸微信」，
但代码里**只有去重、没有状态过滤**。

不过实际不会乱推——因为 `services/wechat_bus.py` 的 `send_intraday`（L121-123）**二次把关**：

```python
confirm_statuses = ('联动确认', '已启动', '二次异动')
if status not in confirm_statuses:
    return {'sent': False, 'reason': '非确认状态，不推送企业微信'}
```

**所以真正推送企业微信的只有 `联动确认` / `二次异动` / `已启动` 三个状态**。

一个可观察点：`二次异动` 推进后若扩散有效，**同轮**会紧接着推 `联动确认`（L1118-1123），
去重键是 `code|status` 所以两条都会发 → 同一只股可能收到「早期启动确认」+「联动确认」两条。
这看起来是有意设计（先给早期提示、再给确认），如果不想要可以合并。
