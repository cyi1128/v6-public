## 一、根因排查结论

### 1.1 此前多次修复不彻底的根本原因

| 修复阶段 | 做法 | 不彻底原因 |
|---------|------|-----------|
| 第一阶段 | 建立 `industry_override.json`（547条单只修正） | 仅覆盖547只，全市场3400+只仍走错误逻辑；override优先级低于full_map |
| 第二阶段 | 创建 `industry_full_map.json`（3423只） | **映射表本身数据源错误**——构建时使用的接口返回了错误分类，如605169洪通燃气被标为"电子" |
| 第三阶段 | 自选股页面加载映射表修复os作用域 | 仅修复了加载异常，未解决映射表数据质量问题 |

### 1.2 错误链路复现（以洪通燃气605169为例）

```
数据源层: industry_full_map.json 第2526行 → "605169": "电子"  ← 根因
缓存层:   industry_cache_v2.json 第2102行 → "605169": "半导体" ← 旧缓存污染
逻辑层:   IndustryFilterService.get_industry()
          优先级: full_map > override > cache > tdx API
          → full_map命中"电子"，直接返回，不再查override
输出层:   ai520_realtime_monitor._build_single_push_message()
          → 行业字段显示"电子"
UI层:     battle_console_v2 从同一signal dict读取industry
          → 显示"电子"
```

**关键发现**: 计算层和输出层共用同一数据源（signal dict中的industry字段），链路本身一致，但数据源（full_map）本身就是错的，导致全量错配。

### 1.3 补丁式代码确认

- `industry_override.json` 存在547条单只修正，但因优先级低于full_map，全量扫描时不生效
- 无其他分支未调用正确分类逻辑的情况
- 旧缓存 `industry_cache.json`（605169="未知"）和 `industry_cache_v2.json`（605169="半导体"）存在数据污染

### 5.1 映射表更新机制

**定期更新**（建议每月执行一次）:
```bash
python tools/rebuild_industry_map_v2.py
```

- 脚本通过 akshare `index_component_sw()` 重新获取全市场申万一级行业分类

**触发更新场景**:
- 申万行业分类调整（通常每半年一次）
- 新股上市后需要纳入映射表
- 发现行业分类错误时

**手动单只修正**（禁止作为常规手段）:
- 仅在映射表重建后仍有个别错误时使用
- 修改 `data/cache/industry_override.json`，格式: `{"代码": "正确行业"}`
- override为最低优先级兜底，不会影响全量扫描

### 5.2 错误告警规则

**日志位置**: `logs/industry_error_YYYYMMDD.log`

**告警触发条件**:
1. 单条推送行业校验不通过 → 立即记录错误日志，自动重取
2. 单日行业错误≥3次 → 自动生成汇总告警日志
3. 重取仍失败 → 临时隐藏行业字段，记录严重告警

**日志内容**:
```
[2026-09-07 13:37:35] [INDUSTRY_ERROR] code=605169 name=洪通燃气 wrong=电子 corrected=公用事业 layer=第一层 reason=公用事业类股票不得为电子
```
